# Spec 03 — 账号登录与用户管理

## Problem Statement

设计保存、清单导出（水印需要用户身份）和未来的 AI 用量控制都需要用户身份；同时开发阶段需要快速可用的登录方式，而生产环境受微信开放平台资质约束，需要一种不阻塞开发、上线后仍保留测试通道的登录策略。

## Solution

按运行环境区分登录方式：开发环境（flag 控制）启用用户名+密码登录；生产环境默认仅微信扫码登录（资质就绪后接入，先预留接口），另有一个不在导航中暴露、需手动输入 URL 访问的隐藏登录页支持账号密码，供线上测试。游客可试用编辑，保存与导出需登录。

## User Stories

1. 作为开发者，我想通过编译/部署 flag 切换 dev 账密登录的可见性，以便开发调试时不依赖微信资质。
2. 作为线上测试人员，我想通过手动输入的隐藏 URL 访问账号密码登录页，以便在生产环境做测试而普通用户看不到入口。
3. 作为普通访客，我想以游客身份进入编辑器试用（浏览与编辑），以便在注册前评估产品。
4. 作为用户，我想注册/登录后保存我的设计与导出清单，以便跨设备继续工作并获得带身份水印的清单。
5. 作为用户（生产环境），我想用微信扫码一键登录，以便最简便地使用产品。
6. 作为用户，我想登出，以便在共用设备上保护我的账号。
7. 作为用户，我想我的密码以不可逆方式存储，以便即使数据库泄露密码也不外泄。
8. 作为用户，我想在登录态过期后收到明确提示并重新登录，而不是静默失败，以便理解为什么保存失败。
9. 作为管理员，我想在后台查看用户列表（ID、昵称、注册时间、状态），以便了解用户情况。
10. 作为管理员，我想封禁/解封用户，以便处置异常账号。
11. 作为用户，我想有一个系统内昵称（注册时默认生成，可修改），以便水印与界面中标识我而不暴露手机号。
12. 作为系统，我想微信登录预留为独立适配器接口（dev 账密为另一实现），以便资质就绪后不影响其他模块接入。

## Implementation Decisions

- 登录方式以策略/适配器模式隔离：`dev-password`（flag 控制）与 `wechat-qr`（生产默认，一期预留接口，可返回"暂未开通"）两个实现；隐藏登录页固定路由、不在任何导航/站点地图中暴露，生产仍可用。
- 会话：服务端签发的 httpOnly Cookie 会话（不使用 localStorage token），登录态过期统一返回明确错误码，前端据此引导重新登录。
- 密码使用强慢哈希（bcrypt/argon2 类）存储；禁止明文或快速哈希。
- 用户唯一身份：一期以系统内用户 ID + 昵称；微信 unionid 字段预留。
- 游客边界：可进入编辑器编辑（内存态），保存/版本/导出接口要求登录；后端所有需登录接口对未登录返回统一 401。
- 后台用户管理一期仅：列表、搜索、封禁/解封。无角色细分（admin 单一角色，通过种子数据生成首个管理员）。
- 不做邮箱/手机号验证码（需求确认改为账密 + 微信）；注册即创建账号，无邀请码。

## Testing Decisions

- API 测试：登录成功/失败（错误密码）、会话过期返回统一 401、游客访问受保护接口被拒、封禁用户登录被拒、隐藏登录页与 dev flag 的组合行为（flag 关闭时 dev 登录接口不可用，隐藏页仍可用）。
- 密码存储只验证外部可观察行为（同一密码可登录、数据库中无明文/可逆痕迹），不测试哈希函数内部。
- 微信适配器：以 mock 适配器测试策略切换与"暂未开通"路径，不做真实微信联调（联调属部署验收，不在自动化测试范围）。

## Out of Scope

- 手机号/邮箱验证码登录、找回密码（一期账号以测试与微信为主；如需找回密码，二期评估）。
- 充值、余额、支付。
- 多角色权限体系（RBAC）。
- 第三方登录（除微信）。

## Further Notes

- 微信开放平台资质办理是外部依赖（requirements §11 开放问题 1）；本 spec 保证接口就绪，上线形式以资质进度为准。
- 生产隐藏登录页的存在属于有意的产品决策（线上测试通道），文档化以防被当作安全漏洞"修复"。
