# Spec 02 — 结构化设计模型、云端保存与版本历史

## Problem Statement

用户的设计需要一种机器可读、可编辑、可校验、可出清单的表示形式；同时设计必须持久保存在云端，且 AI 修改存在改坏的风险，用户需要随时回退到之前的状态。

## Solution

定义唯一的结构化设计模型 JSON Schema（本系统核心接缝）：项目元信息 + 型材件列表 + 封板件列表。所有模块（编辑器、AI、BOM）只通过该模型交互。登录用户的设计自动云端保存，每次生效变更自动形成版本，可一键回退。

## User Stories

1. 作为用户，我想创建一个新的设计项目（命名），以便保存我的家具方案。
2. 作为用户，我的设计在编辑过程中自动保存到云端，以便不用担心丢失工作成果。
3. 作为用户，我想在"我的设计"列表中查看并打开我的历史项目，以便继续之前的工作。
4. 作为用户，我想重命名或删除自己的设计，以便管理我的项目列表。
5. 作为用户，我想每次应用变更（手动编辑生效、AI 修改被应用）后自动生成一个版本记录，以便追溯设计演变。
6. 作为用户，我想查看版本列表（时间与摘要），以便找到想回退的状态。
7. 作为用户，我想一键回退到任意历史版本，以便从"AI 改坏了"中恢复。
8. 作为用户，我想设计模型中的所有长度以 mm 表示、切割长度对齐 0.5mm 精度，以便与供应商下单口径一致。
9. 作为用户，我想设计中的型材件引用知识库中启用的规格（含切割长度、三维位置与朝向、连接方式），以便模型可被渲染与出清单。
10. 作为用户，我想设计中的封板件为自由尺寸矩形板（材质、厚度、宽/高、位置与朝向），以便表达侧板/背板/层板/桌面。
11. 作为用户，未登录时我可以自由编辑但无法保存或生成版本，以便先试用再决定注册。
12. 作为系统，我想拒绝任何未通过 Schema 校验或引用了未启用规格/材质的模型入库，以便数据始终有效。
13. 作为开发者，我想 Schema 校验器同时用于前端、后端与 AI 输出校验，以便单一接缝守住所有入口。
14. 作为用户，我想同一设计在两个标签页编辑时不会产生静默的数据丢失（后写入者得到明确提示），以便避免冲突困惑。
15. 作为 AI 修改功能，我想以"当前模型 JSON + 变更指令 → 修改后的模型 JSON/diff"的方式工作，以便修改可被校验、预览与应用。

## Implementation Decisions

- 设计模型顶层结构（概念）：`meta`（名称、单位 mm、精度 0.5mm）、`profiles[]`（规格代号、切割长度、位置/朝向、连接件引用）、`panels[]`（材质 id、厚度、尺寸、位置/朝向）。
- Schema 为单一权威定义（一份 schema，多端复用）；服务端在保存与 AI 应用两个入口强制校验，并做知识库引用有效性校验（规格/连接件/材质必须存在且启用）。
- 保存采用自动保存（防抖合并），乐观锁版本号处理并发：检测到陈旧写入时返回冲突，由前端提示用户刷新合并，不做自动三方合并。
- 版本历史：每次"生效变更"（保存产生实质差异或 AI 应用 diff）追加版本快照，附摘要（人工编辑/AI 修改及来源摘要）；回退 = 以历史快照创建新版本（前向追加，不改写历史）。
- 删除设计为软删除，保留一段时间以便恢复（时限实施时定，默认 30 天）。
- 未登录游客的设计仅存在于前端内存/会话中，登录后提示可保存为云端项目。
- 不提供设计文件本地导出/导入（需求确认：无目标场景）。

## Testing Decisions

- 核心接缝测试：Schema 校验器对合法/非法 fixture 的行为（缺字段、精度违规、未知规格引用、停用规格引用、超限切割长度）。
- API 测试：设计 CRUD、自动保存冲突（并发版本号）、版本列表与回退语义（回退后产生新版本而非覆盖）。
- 回退与版本是纯数据行为，无需渲染即可完整测试。
- 无既有测试先例；本 spec 与 spec-01 的 API 测试模式作为项目测试范本。

## Out of Scope

- 设计的协作/共享（多人编辑、分享链接）。
- 本地导入导出、文件格式转换。
- 模板市场/公共模板（可作为后续 spec）。

## Further Notes

- Schema 的具体 JSON 字段在实施时以一份独立的 schema 文档/代码为准，本 spec 只锁定概念结构（此处的字段列表为决策性描述，非最终代码）。
- "生效变更"与防抖窗口的具体时长实施时定，行为标准是：用户可感知的每次变更都有对应版本，且不会因连续微调产生海量版本（连续微调合并为一个版本）。
